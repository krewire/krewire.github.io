Onboarding Fast-Track

Start Contributing in 5 Steps

From zero to your first merged pull request. Here is how to get your development environment running in minutes.

1

1. Fork & Clone Repositories

Fork any Krewire repository to your personal GitHub account, then clone it locally to begin:

$ git clone https://github.com/your-username/krewire && cd krewire
2

2. Build the kiw CLI from Source

Inside your clone of the core repository (Go 1.27.1+), build the CLI you are changing:

$ go build -o bin/kiw ./tools/kiw/cmd/kiw && ./bin/kiw version
3

3. Pick an Open Issue

Browse our curated issues list tagged with good first issue or help wanted. Comment to let maintainers know you are working on it.

View Good First Issues →
4

4. Implement & Verify Locally

Write clean, idiomatic Go code and tests. Run the quality gates from CONTRIBUTING.md before opening a pull request:

$ gofmt -l . && go vet ./... && go test ./...
5

5. Submit PR with Conventional Commits

Open a PR following Conventional Commits (feat, fix, docs, refactor, test). Maintainers and AI Boost will review and guide you to merge.

$ git commit -m &quot;feat(web): add handler (ref #123)&quot;
Quality Assurance

The Krewire Way: 3 Quality Gates

To keep the codebase reliable, predictable, and production-ready, every pull request must pass three gates. The canonical list lives in the core repository's CONTRIBUTING.md.

✓

Gate 1: Format & Lint

Zero lint errors and idiomatic Go formatting. Code must adhere strictly to Go standard conventions.

Required: gofmt -l . (clean), go vet ./... (clean)
🛡️

Gate 2: Tests

Every change must pass the module's unit and integration tests, and kiw compat must report ok after version.go changes.

Required: go test ./... passes, kiw compat prints ok
📝

Gate 3: Spec & Commits

Changes must link to a valid Spec or Issue, following Conventional Commits format.

Required: Semantic commit format & spec traceability
Ecosystem Governance

Public RFC Workflow & Architectural Decisions

Krewire operates under transparent open-source governance. All major architectural shifts follow the Request for Comments (RFC) process before becoming permanent Architectural Decision Records (ADRs).

Phase 1

Proposal & Problem

Open a GitHub Discussion in krewire/internal outlining the motivation, trade-offs, and ecosystem impact.

Phase 2

Formal RFC Draft

Submit an RFC PR using the standard template covering API design, failure modes, and migration plans.

Phase 3

14-Day Review

Public comment period for Indonesian and global contributors to review, benchmark, and propose refinements.

Phase 4

Consensus & ADR

Consensus among Maintainers promotes the RFC into an immutable ADR (e.g., ADR-6CAB8C) committed to internal/.

Canonical Architectural Decision Records (ADR Digest)

ADR-6CAB8C: Ecosystem Architecture Baseline & Strict Downward-Only Dependencies

Defines strict unidirectional boundaries: templates/boost → tools/kiw → pkg/* → pkg/model. Zero upward edges allowed.

ADR-C9L2P: Multi-Workload Single Binary Dispatch

Standardizes 8 workload kinds behind krewire.yaml and unified CLI kiw with zero framework lock-in.

ADR-D1F3N: Zero-Trust Defense-in-Depth Edge Security

Requires CSRF token verification, ACME automated TLS, token bucket rate limiting, and secure HTTP response headers across all daemons.

Support Krewire

Supporting Krewire's Long-Term Maintenance

Krewire measures success by what developers build with it, not by money raised. Support, financial or not, is how the project stays maintained: it pays for maintainer time and infrastructure so that the open-source core keeps working for everyone.

Current Status: No Active Funding Channel

Krewire does not accept donations or sponsorships yet. The core repository's FUNDING.yml names a GitHub Sponsors account, but that profile is not active, so there is nothing to link to. A funding channel will appear here only after it is live and verified. There are no sponsorship tiers, perks, or published financial figures.

What Support Makes Possible

Maintenance

Reviewing issues and pull requests, and keeping the Go packages and the kiw CLI working across releases.

Documentation

Keeping the guides on krewire.com accurate and in step with the code, in English and Indonesian.

Security

Triaging vulnerability reports and keeping dependencies and secure defaults up to date.

Community

Onboarding new contributors and answering questions from people building with Krewire.

Collaborating with AI Boost

Krewire pioneers the collaboration between human maintainers and autonomous AI agents. Our AI Boost framework operates with strict verification standards:

  • Automated Architecture Audits: AI agents check PRs against KWF-* specifications.
  • Continuous Regression Hunting: Agents synthesize edge cases and race condition checks.
  • Transparent Pair Programming: AI agents explain architectural decisions openly in discussions and PR comments.
  • Human Governance: Ultimate merging authority always remains in the hands of human collective maintainers.
